Règles de détection

Canaux de notification

Politiques de notification

Aucune politique = fan-out plat vers TOUS les canaux (comportement par défaut). Une politique route une alerte (par label) vers des canaux précis ; la plus spécifique gagne ; une route sans matcher = route par défaut.

Silences (mute temporisé)

Mute les alertes correspondant à {champ=valeur,…} jusqu'à expiration (auto-expire). Ledgerisé (qui, quoi, jusqu'à quand). Un silence ne peut être permanent (TTL borné).

Parsers (extraction de champs)

Extrait des champs (groupes nommés regex (?<nom>…)) du message à l'ingestion, pour toutes les sources (k3s / hôte / conteneur — le parsing est central, indépendant du mode). Défauts intégrés (désactivables) + tes parsers custom. source=* = toutes.
Quand ? un parser est effectif dès l'enregistrement, sur les nouveaux events. Pour les anciens : ↻ Réappliquer (rétroactif, avec confirmation) — ou | rex à la volée dans une recherche.
Sens IP : nomme src_ip = l'initiateur (l'attaquant en entrant), dst_ip = la cible. src_ip/rhost sont promus en colonne cherchable ; une IP de sens incertain → laisse-la en champ neutre (ex ip), jamais src_ip.

Playbooks — règles de réponse

...

Un playbook est une règle de réponse : une condition (la requête, dont la 1re colonne = la cible), une action, un interrupteur. Évalué à intervalle régulier. Il n'exécute RÉELLEMENT que lorsque le mode ci-dessus est Actif ; en Observation, il ne fait que proposer. Ce n'est pas un guide d'incident : pour une checklist attachée à un cas, voir les runbooks ci-dessous.

Runbooks — guides d'incident

Un runbook est un guide d'incident : des étapes phasées, attachées à un cas élevé en incident. Aucune condition, aucun exécuteur : rien ne se déclenche seul. Les livrés sont immuables en place — activez/désactivez ou clonez pour personnaliser ; les custom sont pleinement éditables. Une étape search passe par le compilateur GXQL fermé ; une étape response ne référence que l'enum d'action (exécution via /api/actions, approbation + ledger).

Actions

File de riposte : chaque action (ban_ip, unban_ip, kill_pid, stop_service) est créée en attente d'approbation ; en dry-run elle est simulée, sinon elle est exécutée réellement après approbation.

Risque par entité (RBA)

Alerting basé sur le risque : chaque signal (règle en mode risque, match threat-intel…) contribue un score à son entité (IP, hôte, utilisateur…). Le tableau agrège le score cumulé, la vélocité (score récent), le nombre de contributions et de tactiques MITRE distinctes — servi du rollup (aucun scan d'events). Le badge seuil marque les entités au-dessus d'un seuil. Clique une ligne pour sa timeline et ses contributions. Lecture seule.

Comptes vus par l'authentification

    
Chaque compte qui a atteint cette console, quelle que soit sa provenance : ce que la liste ci-dessus ne peut pas montrer. Un compte d'annuaire externe n'est ni créé ni géré ici — son rôle vient de ses groupes, et il se révoque dans l'annuaire.

    

  

  
  

    

      
Jetons (agent & HEC) 

      
    

    
Un jeton authentifie une machine (Bearer) sans mot de passe partagé. agent : ingestion + réponse (le responder exige un jeton lié à un hôte). HEC : forwarder compatible Splunk HTTP Event Collector → POST /services/collector avec l'en-tête Authorization: Splunk <jeton>. Le secret n'est affiché qu'une seule fois à la création (seule son empreinte SHA-256 est conservée) : copie-le immédiatement. Réservé admin.

    

  

  
  

    

      
Identité fédérée (SSO)

      
    

    
Fédère l'authentification via OIDC (Google/Azure AD/Okta/Keycloak/Authentik/générique — Authorization-Code + PKCE, validation JWT via JWKS) ou LDAP/AD (bind). Les groupes de l'IdP sont mappés vers un rôle Plume (admin/editor/viewer) selon la même table que le SSO d'en-tête. Le secret (client_secret / mot de passe de bind) est chiffré au repos et n'est jamais réaffiché. Tant qu'aucun fournisseur n'est activé, l'auth existante est inchangée. Réservé admin.

Field filters (masquage PII)

      
    

    
Masque un champ d'événement (ex src_user, email, message, src_ip) pour les rôles bas. Actions : masquer (***), partiel (***+4 derniers, ex PAN), hacher (déterministe salé — corrélation préservée, non réversible), supprimer (NULL) ou interdire (tous rôles, admin compris). Le masque est appliqué DANS le SQL compilé : Recherche/GXQL, panneaux, export, recherche et timeline de cas en héritent AUTOMATIQUEMENT, agrégations comprises (| stats values(src_user) ne fuit pas), et le filtrage sur un champ masqué est refusé (pas d'oracle). Par défaut l'admin voit en clair ; « interdire » s'applique à tous. Portée d'« interdire » en SQL brut : sur une colonne réelle (host, src_ip, dst_ip, url, message, source, category), l'interdiction est aussi imposée par l'authorizer SQLite — bloquée même en SQL brut admin ; sur une clé du sac JSON (src_user, email, pan, fields.*), un admin peut encore la lire en SQL brut via json_extract(fields,'$.pan'). Pour un blocage PCI dur d'un tel champ, pose l'« interdire » sur une colonne réelle, ou masque à l'ingestion (processeur #40). Tant qu'aucune règle n'existe, toute lecture est inchangée. Réservé admin.

Lookups (tables d'enrichissement) 

      
    

    
Une table de référence nommée (clé → colonnes) qui enrichit les événements via l'opérateur GXQL lookup <nom> <champ-clé> [OUTPUT cols] (jointure LEFT JOIN). Ex : un lookup geoip de clé ip → {country, asn} permet search source=web | lookup geoip src_ip OUTPUT country pour ajouter le pays à chaque événement. Lecture pour tous les rôles ; création/suppression réservées éditeur et admin (viewer = lecture seule). L'upload remplace intégralement le contenu du lookup (les colonnes de sortie sont déduites des lignes) et accepte le collage en JSON (tableau d'objets) ou en CSV (1re ligne = en-têtes).

Processeur d'ingest

      

        
        
      

    

    
Des règles ordonnées décident ce que le SOC n'indexe PAS (levier de rétention n°1). Chaque règle a un prédicat (sur le modèle CIM normalisé : catégorie / source / champs) et une action : DROP (n'indexe pas), MASK (masque un champ — PII), ROUTE (pose l'environnement / classe de rétention), SAMPLE (garde 1 event sur N d'une source bruyante). Appliquées à l'ingest, juste après normalisation, avant écriture. Aucune perte silencieuse : tout event non-indexé est compté et visible ci-dessous. Une règle invalide est ignorée (l'event est indexé inchangé). Réservé à l'administrateur.

    

    

  


  
  

    

      
Indexes & rétention

      

        
        
      

    

    
Un index logique nommé = la valeur env_id d'un event — le même axe que route l'action ROUTE du processeur d'ingest (#40) et qu'agrègent les rollups. Définis une rétention propre par index (ex : auth 400 j, debug 7 j) et des plafonds optionnels (nombre de lignes / taille estimée). Un index sans politique hérite de la rétention globale. Une fenêtre est planchée à 7 j (anti-effacement) ; les events de contrôle du daemon ne sont jamais purgés. Pour router un index HEC (fields.index) vers un env, crée une règle #40 match fields.index eq <x> → route env=<x>. Les comptes / plus ancien / taille sont estimés (rollups). Réservé à l'administrateur.

    

    

  


  

    

      
Connecteurs de sources 

      

        
        
        
        
        
      

    

    
    

    
Branche une source externe en PULL : le daemon interroge périodiquement l'API, normalise les alertes au schéma event (source=defender, sévérité mappée, titre/catégorie, entités → champs) et les ingère dans ce tenant. Microsoft Defender (Graph Security API, OAuth2 client-credentials) est le premier connecteur — Windows/Sysmon, Linux/macOS et mobile viendront. Le client secret est un credential stocké chiffré au repos : il n'est jamais réaffiché (masqué •••) et n'est ré-envoyé que si tu le re-saisis. Un nouveau connecteur est créé désactivé : Teste la connexion puis active-le. Un connecteur en panne est journalisé (dernière erreur) sans casser les autres. Réservé à l'administrateur.

Destinations de sortie

      

        
        
      

    

    
Forwarde les events normalisés/filtrés vers une cible externe : syslog (RFC5424 sur TCP), HEC-out (Splunk HTTP Event Collector) ou webhook (POST JSON) — S3 & Kafka sont en design/stub. Plume peut ainsi servir de couche collecte + normalisation devant un autre SIEM, ou de forwarder d'archive froide. Un filtre allowlisté (catégorie CIM / environnement / source / sévérité min — jamais de SQL libre) décide quels events sortent. Livraison at-least-once par curseur (watermark = dernier event.id forwardé), lot borné, envoi réseau hors du chemin d'ingest : un sink lent/mort ne bloque JAMAIS la collecte (watermark gelé, ré-essai au tick suivant). Surface de sortie de données : l'auth du sink (jeton HEC / en-tête webhook) est un credential stocké chiffré, jamais réaffiché ; toute création/activation/suppression est journalisée (ledger). Une destination reçoit des events bruts non masqués (feed machine) — c'est pourquoi elle est réservée à l'administrateur.

Suppressions & whitelists actives 

      
    

    
Vue unique de TOUS les filtres/suppressions/whitelists actifs, quel que soit leur périmètre — collecte et règles NON modifiées depuis cette console. Chaque entrée porte son type : display-only (de-bruite un panneau seul, jamais la détection) · collection-reducing (réduit l'ingestion — read-only, contrôle à la frontière hôte) · host (état firewall/enforcement — read-only). Seule l'exclusion d'affichage opérateur / self (prouvée display-only) est éditable ici (confirmée + auditée) ; elle ne peut créer aucun angle mort. Un seul écran → aucune suppression cachée.

Rétention des données 

      
    

    
Durées de conservation des données (valeurs effectives). Réduire une durée est destructif : les données plus anciennes seront purgées au prochain cycle horaire. Toute baisse exige une confirmation et est inscrite au journal d'audit. Les alertes ouvertes ne sont jamais purgées.

Tenants 

      

        
        
      

    

    
Espaces clients isolés (base chiffrée dédiée par tenant). Créer / suspendre / supprimer un tenant est réservé au super-admin plateforme ; un admin de tenant gère uniquement les accès de son propre tenant. La suppression est une destruction cryptographique irréversible (clé oubliée + base détruite) et exige de retaper le nom. Toute action est auditée. La vraie garde reste serveur.

Threat Intel (IOC)

      

        
        
        
      

    

    
Magasin d'indicateurs de compromission (IOC) du tenant. Le match-on-ingest enrichit les events qui matchent (fields.threat_intel, ti_match=1) — il n'écrase ni ne supprime rien. Types : ip · domain · url · hash_md5 · hash_sha1 · hash_sha256 · email. Ajout manuel, import d'une liste (type,valeur par ligne) ou d'un bundle STIX 2.1. Les hits dans le temps se requêtent dans la Recherche (GXQL). Ajout / import réservés à l'administrateur (la vraie garde reste serveur).
